# WMS ↔ Scenario Manager 재고 동기화

WMS(창고 실물 장부)를 기준으로 Scenario Manager(SM)의 오브젝트 수량과 대여 상태를 맞춘다.

## 왜 관리자 PC에서 도는가

- SM은 테일넷 안에서만 열린다. WMS 서버(미니PC)는 2026-08-26에 Tailscale을 껐으므로 SM에 닿지 못한다.
- 브라우저의 WMS 화면도 다른 도메인인 SM을 조작할 수 없다.
- 그래서 **테일넷에 붙어 있고 SM에 로그인된 관리자 PC**가 중간에서 다리를 놓는다.

SM에는 `actor_id`(처리한 관리자)와 `borrower_id`(실제 대여자)가 따로 기록된다.
처리 계정은 그 PC에 로그인해 둔 관리자 본인이고, 대여자는 WMS 데이터에서 온다.

**비밀번호는 저장하지 않는다.** 자세한 내용은 아래 설치 항목에 적었다.

## 설치 (관리자 PC마다 1회)

1. `setup.cmd` — 의존성만 설치한다.
2. `register-task.cmd` — 로그온할 때마다 에이전트가 자동 실행되도록 등록한다.

**SM에 따로 로그인하지 않는다.** WMS 관리자 계정과 SM 계정이 같으므로, 관리자가 WMS에
로그인하는 순간 그 자격증명이 이 PC의 에이전트(`127.0.0.1:8787`)로 전달되고,
에이전트가 SM에 로그인해 세션을 만든다.

- 비밀번호는 **로그인 요청에만 쓰고 즉시 버린다.** 파일에도 로그에도 남기지 않는다.
- 세션 쿠키는 **에이전트 프로세스의 메모리에만** 있다. 그래서 PC를 껐다 켜거나 에이전트를
  다시 시작하면, 관리자가 WMS에 다시 로그인할 때까지 동기화가 멈춘다 —
  자격증명을 디스크에 두지 않기 위해 감수하는 부분이다.
- 자격증명은 루프백(127.0.0.1) 밖으로 나가지 않는다. 에이전트는 WMS 화면에서 온 요청만 받는다.
- 세션이 없는 동안 생긴 변화는 사라지지 않는다. 상태를 갱신하지 않고 미뤄두었다가,
  로그인되면 그때 한꺼번에 처리한다.

## 상시 동기화

`agent.mjs`가 15초마다 WMS를 확인해, **대여 확인·반납으로 달라진 물품만** 골라
수량 → 대여 순서로 SM에 반영한다. 전체를 훑지 않으므로 한 회차가 몇 초면 끝난다.

```
node agent.mjs                    에이전트 시작 (127.0.0.1:8787, 15초 간격)
node agent.mjs --port=9000 --interval=30
node agent.mjs --dry-run          무엇을 처리할지 기록만, 쓰지 않음
curl http://127.0.0.1:8787/status 로그인 여부 확인
```

기록은 `agent.log`에, 마지막으로 본 상태는 `.watch-state.json`에 남는다.
첫 실행은 "지금 상태"를 기준으로 삼고 그 이후의 변화부터 따라간다.

SM에는 `actor_id`(처리한 관리자 = 로그인한 계정)와 `borrower_id`(실제 대여자)가 따로 남는다.

## 수동 실행 (밀린 차이 한꺼번에 맞추기)

에이전트는 "지금부터의 변화"만 따라간다. 설치 시점에 이미 벌어져 있던 차이는 아래로 맞춘다.
이 두 스크립트는 에이전트와 달리 브라우저(Chrome) 세션을 쓰므로 `node sync.mjs --login`으로
한 번 로그인해야 한다.

```
node sync.mjs                       수량 차이만 확인 (아무것도 쓰지 않음)
node sync.mjs --apply --max=50      수량 반영 (한 번에 최대 50건)
node sync.mjs --ids=000008,000020   특정 물품만

node borrow.mjs 000008              대여 차이 확인
node borrow.mjs 000008 --apply      대여 반영 (모자란 만큼만 - 여러 번 돌려도 안전)
node borrow.mjs --from-report       직전 보고서의 대여 불일치 건 전체
node borrow.mjs 000008 --reset --apply   기존 대여를 되돌리고 처음부터 다시
```

`sync.mjs`는 기본이 확인용이고, 실제로 쓰려면 `--apply`를 붙여야 한다.
`--max`는 한 번에 고칠 최대 건수로, 실수로 수백 건이 나가는 것을 막는다.

## 무엇을 맞추고 무엇을 안 맞추나

- **총 보유 수량**: `POST /object_inventory_quantity`로 맞춘다. note에 출처와 대여 내역을 남긴다.
- **대여 수량**: `POST /object_inventory_event`(action=borrow/return)로 사람별로 맞춘다.
  화면의 Borrow/Return 버튼이 부르는 것과 같은 요청이다.
- **재고를 추적하지 않는 오브젝트**(`_inventory.is_tracked = false`)는 건드리지 않는다.
  이런 오브젝트는 `quantity`가 -1(수량 미등록 기본값)이라 그대로 비교하면 전부 불일치로 잡힌다.
- **WMS에 없는 오브젝트**(SM에만 있는 2800여 종)는 손대지 않는다.

## 사번

SM은 대여자를 사번으로 식별한다(`borrowers: { "1079": 3 }`).

- cfgw 인원: 대여할 때 받은 사번이 이메일(`{사번}@cfgw-kr.com`)에 들어 있다.
- ConfigDS 인원: 사번을 받지 않으므로 **WMS 연결 설정 > ConfigDS 직원 명부**에 적어둬야 한다.
  이 사번은 SM에 적을 때만 쓰이고, WMS 내부의 대여자 식별에는 관여하지 않는다.

사번을 모르는 대여자가 있으면 실행할 때 경고가 뜬다. 그대로 두면 이름 문자열로 들어가
그 사람의 "내 대여" 목록에 잡히지 않는다.
